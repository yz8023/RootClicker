# 对比：clickdevice_android 有什么值得学

参考项目：[ming123aaa/clickdevice_android](https://github.com/ming123aaa/clickdevice_android)（Kotlin、Compose、Room，基于**无障碍服务**的连点器；仓库 159 个文件，最近更新 2026-11-11）。

本文记录三件事：它能做到而我们没做的、它的优点、我们的缺点，以及这一版真正搬过来的东西和**故意不搬**的东西。

---

## 一、它的功能清单 vs 我们

| 功能 | clickdevice_android | RootClicker（1.4.0 之前） | 结论 |
| --- | --- | --- | --- |
| 点击注入方式 | 无障碍 `dispatchGesture` | root + `app_process` + `InputManager.injectInputEvent` | 我们更好：不用每次授权、延迟毫秒级、可同帧多指 |
| 精确坐标点击 | ✅ | ✅ | 已具备 |
| 手势轨迹（滑动） | ✅ | ✅ 录制回放里支持 | 已具备 |
| 随机区域点击 | ✅ | ✅ 坐标抖动 `jitterPx` | 已具备（全局） |
| 每点点击时长 / 延时 | ✅（脚本命令粒度） | ✅ 1.2 起支持（每点独立） | 已具备 |
| 脚本命令编辑器（手写点击/延时/循环 + 拖拽排序） | ✅ | ❌ 只有录制出来的脚本 | **未搬**（见第四节） |
| 脚本 JSON 导入 | ✅ | ❌ | **未搬**（下一版候选） |
| 脚本分组（把多个脚本串成一个动作） | ✅ | ⚠️ 有模板（只存参数） | 见下 |
| **整套配置（点位 + 参数）保存 / 切换** | ✅（脚本表 / 分组表） | ❌ 只有单份配置 + 参数模板 | **已搬**：新增「方案」 |
| **桌面快捷方式一键跑** | ✅ | ❌ | **已搬**：为方案固定桌面快捷方式，点了直接开跑 |
| **悬浮窗位置锁定 / 记忆** | ✅ | ❌ 每次都回到默认位置 | **已搬**：位置写进配置，下次原地出现 |
| **切到别的应用自动停止** | ✅ | ❌ | **已搬**：可选开关，默认关 |
| 多个悬浮快捷按钮绑定不同脚本（最多 5 个） | ✅ | ⚠️ 一条控制条 | **未搬**（和「极简」冲突） |
| 坐标系数缩放 0.25x~5x | ✅ | ✅ `normalizeTo(baseWidth, baseHeight)` | 已具备 |
| 悬浮窗控制（自由拖拽） | ✅ | ✅ 拖动握把 | 已具备 |
| 录制屏幕操作 | ✅ | ✅ root 直读 `/dev/input` | 我们更准（原始事件，不是无障碍回调） |
| 数据库 | Room | JSON 文件（人可读、可直接备份） | 取舍问题，见第四节 |
| 迁移/版本升级友好 | ✅ Room + migration | ⚠️ JSON 加字段靠 `ignoreUnknownKeys` 兜底 | 够用，但不如 Room 稳 |

## 二、它的优点（客观）

1. **功能密度高**：脚本命令、脚本组、按键绑定、快捷方式、参数体系（间隔/次数/速度/坐标系数）一层层都能配，属于"重度自动化工具"。
2. **持久化做得正规**：Room + DAO + Bean，数据模型和界面分得清楚，加字段有 migration。
3. **按键绑定这个交互很聪明**：悬浮窗上最多 5 个自绘按钮，每个绑一个脚本，颜色/字号可调，等于把"多个入口"塞进一个悬浮窗。
4. **桌面快捷方式**：把"打开应用 → 找脚本 → 点运行"压成桌面一个图标。
5. **切应用自动停止**：防止连点在切走的界面里乱点，安全。
6. **README 写得好**：功能、技术栈、组件表、目录树、使用步骤都有，别人一眼能看懂。
7. **模块划分干净**：`activity / bean / db / helper / view / vm`，找东西很快。

---

## 三、我们的不足（诚实版）

1. **配置只有一份**：之前只能"当前这一套点位 + 参数"，模板只存参数。想做"游戏 A / 游戏 B"就得重新取点。—— 1.4.0 用**方案**解决。
2. **没有导出/备份**：换机、清数据就没了。JSON 文件在 `files/clicker.json`，但要 root 才能拿到。
3. **没有桌面快捷方式**：每次都要先开应用或下拉磁贴。
4. **悬浮条位置不记忆**：每次启动都回到屏幕 1/4 处。
5. **没有"切走就停"**：连点跑着的时候切到别的应用，会继续点，容易误触。
6. **权限引导一塌糊涂**：首次进入的检测页是模板自带的"系统版本 / 视觉效果 / 通知"，说的是 ZeroUI 模板的话，不是我们的权限；说了"不符合要求"却没说**要去哪给、给完怎么回来**。—— 1.4.0 重做。
7. **没有手写脚本编辑器**：只有"录一遍再回放"，没法精确手改某一步。
8. **没有导入别人的配置**：只能自己取点。

## 四、1.4.0 真正搬过来的（附实现位置）

| 学到的东西 | 实现 |
| --- | --- |
| 整套配置保存/切换（对应它的脚本+分组） | `ClickPlan`（点位 + 全部参数）+ `ClickerStore.savePlan / applyPlan / updatePlanFromCurrent / deletePlan`；主页「方案」分组；`activePlanId` 记住当前方案 |
| 桌面快捷方式一键跑 | `core/Shortcuts.kt`（`ShortcutManagerCompat.requestPinShortcut`）+ `MainActivity` 处理 `RUN_PLAN`：套用方案 → 起服务 → 开跑 → 退到后台 |
| 悬浮窗位置记忆 | `EngineOptions.barX/barY`，拖动结束写回，下次 `attachBar()` 用存下来的坐标 |
| 切应用自动停止 | `EngineOptions.stopOnAppSwitch` + `ClickerService.startAppWatch()`：用 root 每 2.5 s 读 `dumpsys window` 的 `mCurrentFocus`，包名变了就 `stop()` 并提示切到了谁 |
| 权限引导要"说清楚 + 直接跳 + 回来重检" | `feature/setup/SetupScreen.kt`：root / 悬浮窗 / 通知 三项必须，电池白名单 / 自启动 两项建议；**点整行就跳到对应系统页**，`LifecycleResumeEffect` 在回到应用时**自动重新检测**；主页顶部有「还差 N 项权限」横幅 |

## 五、故意没搬的，以及为什么

1. **无障碍服务**。它的核心是 `AccessibilityService`。我们走 root 就是为了不要那个：不需要每次重新授权，注入延迟低一个数量级，还能同帧多指。这是我们的立身之本，不换。
2. **Room**。它的数据模型是"脚本 → 脚本组 → 按键绑定"多层，用 Room 合理。我们是"一份配置 + 若干方案 + 若干录制脚本"，一个 JSON 文件就够，还能直接读、直接备份。等方案数量大到需要检索再换 Room 不迟。
3. **手写脚本命令编辑器（点击/延时/循环 + 拖拽排序）**。功能上确实强，但它和"简单上手"直接冲突：用户刚说"内容很复杂，上手很难"。如果要做，应该做成**进阶页**（默认藏起来），而不是放到主页。等你确认要，我再加。
4. **悬浮窗多按钮绑定**。它的 5 个按钮是"多个脚本的快捷入口"。我们要保持一条控制条，多了就回到复杂。方案切换 + 桌面快捷方式已经能覆盖"多个入口"。
5. **JSON 导入导出**。还没做，但方案的数据结构已经是 `@Serializable`，加"导出到剪贴板 / 从剪贴板导入"是几十行的事，列在下一版。

---

## 六、下一步建议（按性价比排序）

1. 方案导出 / 导入（剪贴板 JSON）——换机、分享配置。
2. 方案长按重命名。
3. 进阶的"手势序列"页（默认折叠），把录制和手写命令合一。
4. 条件点击支持"局部图像匹配"，比单像素容差更稳。
